# DOMANGCHA v4.1.0 — LOOP 프로젝트 자율개발 루프 프로토콜

이 파일은 유일한 전체 작업 규정이고 상시 로드하지 않음, CLAUDE.md 핵심이 가리키는 절만 그때 읽음
이 프로젝트의 규정은 전역 규정(~/.claude/CLAUDE.md 의 DOMANGCHA 전체 설치본)보다 우선함
프로젝트 고유 관례는 하단 부록에만 추가하고 본문은 손대지 않음
중량 규정(DOMANGCHA 하네스)은 .claude/heavy/CEO.md 에 두고 모드가 중량인 항목에서만 읽음

슬래시 커맨드는 선택 사항이고 자연어 지시만으로도 이 프로토콜이 동작함
UserPromptSubmit 훅이 매 프롬프트를 지시 또는 개입으로 기록하고 다음 행동과 활성 정책을 함께 출력하므로
훅 출력에 나온 지시를 그대로 따르면 됨

## 0 상태와 도구

- 유일한 재개 근거: .loop/PLAN.md, 컨텍스트가 초기화되어도 이 파일만으로 다음 항목부터 이어감
- 누적 정책: .loop/POLICY.md, 자체감사로 승격된 반복 실수 목록이고 매 항목 감사에서 전 줄 대조
- 기록 CLI: node scripts/loop.mjs (아래에서 loop 로 표기), 지시 개입 구현 기록은 .loop/loop.db 에 저장
- 훅이 자동 기록하는 것: 사용자 프롬프트(지시 또는 개입), 파일 편집, 세션 시작, 컨텍스트 압축
- 에이전트가 직접 기록하는 것: loop plan new, plan check, plan confirm, plan revise, start, pass, fail, hold, final
- 세션 시작 직후와 컨텍스트 정리 직후 첫 행동: loop resume 출력 확인 (훅이 자동 출력, 보이지 않으면 직접 실행)

## 1 루프 1 계획 우선 실행

새 지시를 받으면 코드에 손대기 전에 아래 순서로 진행
슬래시 커맨드 없이 자연어로 받은 지시도 동일하게 이 절차를 적용

플랜을 만들지 않는 예외 (이때는 바로 답하고 끝냄)
- 질문 조회 설명 요약 코드 읽기처럼 저장소를 바꾸지 않는 요청
- 오타 한 줄 수정처럼 감사 기준을 세울 것도 없는 자명한 변경
- 위 둘에 해당하는지 애매하면 플랜을 만드는 쪽을 택함

1 loop resume 으로 활성 플랜 유무 확인, 활성 플랜이 있으면 새 지시는 개입으로 취급하고 2절 개입 처리 적용
2 loop plan new --title "제목" --instruction ins_xxxx --target vX.Y.Z 실행 (ins 번호는 훅 출력에 있음, 목표 버전은 package.json 현재 버전에서 기능 추가는 minor, 버그 수정은 patch 상승)
2a 사용자 기능 요청이면 9절 1항 목적 사슬을 먼저 적어 목표와 항목의 근거로 삼음
   목적 - 진입 경로 - 수행 작업 - 필요한 하위 기능 - 데이터와 상태 - 권한과 외부 의존성 - 성공 결과 - 실패 복구 경로
   요청 문장에 없지만 목적 달성에 필요한 하위 기능은 항목으로 만들고 근거가 필요한 가정은 확인 대상으로 분리
3 .loop/PLAN.md 의 목표, 범위 밖, 완료 정의, 참조, 항목을 작성
4 loop plan check 가 통과할 때까지 수정
5 plan_confirm 설정이 true 이면 플랜 요약(항목 수, 목표 버전, 범위 밖)을 사용자에게 보이고 응답을 기다린 뒤 확인을 받고 loop plan confirm
6 plan_confirm 설정이 false 이면 즉시 loop plan confirm

항목 작성 규칙

- 한 항목은 한 번의 자가감사로 판정 가능한 단위 (변경 파일 5개 이내, 감사 기준 1개 이상 4개 이하 권장)
- 범위: 변경할 파일 또는 디렉터리 나열, 신규 파일은 "신규" 표기
- 감사 기준: 실행 가능한 명령과 기대 결과 또는 관측 가능한 조건만 기재, "잘 동작함" 같은 추상 표현 금지
- 의존: 선행 항목 ID, 없으면 "없음"
- 모드: 경량이 기본, 결제 인증 권한 데이터 삭제 외부 API 비밀 취급 항목은 중량
- 순서: 스키마, 서버, 화면, 다국어, 문서 순이 기본이고 의존 관계가 순서를 결정
- 삽입 항목 ID 는 앞 항목 번호에 소문자를 붙임 (I03 뒤 삽입은 I03a), 기존 번호 재부여 금지
- 항목 삭제는 상태를 취소 (사유) 로 바꾸고 줄은 남김

## 2 루프 2 항목 구현과 자가감사

항목마다 아래를 반복하고 통과 전에는 다음 항목에 손대지 않음

1 loop start Ixx 실행, 출력된 항목 블록의 범위와 감사 기준을 작업 기준으로 삼음, 중량 모드면 heavy_doc 를 먼저 읽음
2 범위 안에서 구현
3 자가감사 8항 실행
  a 범위 일치: git status 의 변경 파일이 항목 범위와 일치, 범위 밖 변경은 되돌리거나 사유를 요약에 기록
  b 정적 검사: cmd_typecheck 통과, lint 설정이 있으면 cmd_lint 통과
  c 항목 감사 기준: 기준 줄마다 실제 실행 또는 확인, 근거를 한 줄씩 확보
  d 비밀과 설정: diff 에 키 토큰 비밀번호 없음, 새 설정값은 env 추가 대신 DB 저장과 UI 관리 (기존 env 키 재사용은 허용)
  e 다국어: 신규 사용자 노출 문자열은 전부 i18n 키, 기본 언어와 영어 메시지 파일 동시 갱신
  f 부작용: 다른 항목의 통과 조건을 깨뜨리지 않음, 관련 테스트 재실행
  g 정책 준수: loop policy check 를 실행해 활성 정책 전 줄을 이번 변경분에 대조,
    어긴 줄이 있으면 loop policy hit P00x --note "무엇을 어겼는지" 기록 후 고치고 다시 대조,
    정책을 어긴 채로 pass 하지 않음
  h 사용자 기능: 이 항목이 사용자 기능이나 화면을 바꿨으면 8절 화면 감사 10문항과 9절 완결성 검증을 모두 수행,
    실제 브라우저에서 확인한 흐름과 확인하지 못한 범위를 근거에 남기고 실행하지 않은 검증을 통과로 적지 않음,
    바꾸지 않았으면 해당 없음이라고 근거에 한 줄 남김
4 판정
  - 전부 충족: loop pass Ixx --summary "어떻게 구현했는지" --notes "감사 근거 요약 + 정책 대조 결과", 커밋은 CLI 가 목표버전-항목ID 메시지로 자동 생성
  - 항목 안에서 고칠 수 있는 미충족: loop fail Ixx --reason "사유" 기록, 수정 후 loop start Ixx 로 재착수하고 3으로
  - 플랜 자체를 바꿔야 하는 미충족: 5로
5 플랜 갱신 (루프의 본체)
  트리거
  - 선행 작업 누락 발견: 현재 항목 앞에 항목 삽입
  - 후속 작업 발견: 뒤에 항목 추가
  - 항목이 한 번에 감사 불가능할 만큼 큼: 둘 이상으로 분할
  - 감사 기준이 틀렸거나 부족: 기준 수정
  - 사용자 개입으로 범위 변경: 항목 추가 수정 취소
  - 외부 요인으로 진행 불가: loop hold Ixx --reason "사유"
  절차: PLAN.md 항목 수정, loop plan revise --level patch|minor --note "무엇을 왜" --ref audit:Ixx 또는 --ref iv_xxxx, 갱신된 플랜 기준으로 2절 계속
  버전 규칙: 항목 추가 수정 분할은 patch, 사용자 개입으로 목표나 범위가 바뀌면 minor
6 한계값 (loop config 로 조정)
  - max_audit_retries (기본 3): 같은 항목 시도 초과 시 loop hold 후 사용자에게 판단 요청
  - max_plan_revisions_per_item (기본 3): 같은 항목 기인 플랜 갱신 초과 시 사용자에게 판단 요청

개입 처리

- 사용자 프롬프트는 훅이 iv_xxxx 로 기록, 에이전트는 그 개입이 플랜을 바꾸는지 판단
- 바꾸면 5절 절차로 반영 (--ref iv_xxxx)
- 바꾸지 않으면 답변 후 계속, 항목 통과 시 CLI 가 자동으로 흡수 처리
- 현재 플랜과 무관한 새 기능 요청이면 현재 플랜 완료 후 새 플랜으로 분리할 것을 제안
- "멈춰" "중단" 계열이면 즉시 loop hold 또는 loop plan abort 후 이유 기록

## 3 컨텍스트 정리와 재개

- 정리 시점 두 가지: 도구의 자동 압축 (시점은 도구가 판단), 사용자의 수동 /clear
- 자동 압축 시점을 예측하지 않음, 대신 항목 통과마다 PLAN.md 가 최신이 되므로 언제 정리되어도 손실 없음
- loop pass 출력에 체크포인트와 /clear 권장이 나오면 사용자에게 그대로 전달 (checkpoint_every 개 통과마다 표시)
- 정리 후 재개 절차
  1 loop resume 출력 확인 (SessionStart 훅이 자동 출력)
  2 상태가 진행중인 항목이 있으면 구현 상태가 불명이므로 loop start Ixx --force 후 2절 3의 자가감사부터 다시 수행
  3 없으면 첫 대기 항목부터 2절
  4 플랜 파일과 DB 기록이 다르면 플랜 파일 우선
- 재개 시 이전 대화 내용을 추정하지 않음, 필요한 사실은 PLAN.md, git log, loop history 에서만 취함

## 4 종합 자가감사

전 항목 통과 후

1 cmd_typecheck, cmd_lint, cmd_test, cmd_build 전체 실행
2 완료 정의 각 줄 확인
3 전체 diff 검토: git diff <시작 커밋>..HEAD --stat (시작 커밋은 PLAN.md 헤더), 범위 밖 변경 없음, 비밀 없음, 하드코딩 문자열 없음
4 항목 대 결과 대조: 각 항목 범위의 파일이 실제로 존재하거나 변경됨
5 loop policy check 로 활성 정책 전 줄을 전체 diff 에 대조, 위반 0건 확인
5a 이번 플랜이 사용자 화면을 바꿨으면 8절 감사를 대표 사용자 흐름 하나에 끝까지 적용하고 나머지 화면으로 확장
5b 사용자 기능을 바꿨으면 9절 완료 조건 8줄을 대조하고 확인하지 못한 항목은 완료로 적지 않고 남은 제한으로 분리
6 이번 플랜에서 policy hit 가 있었으면 그 정책이 실효성이 있었는지 판단하고 필요하면 문구를 다시 씀
7 결과를 PLAN.md 종합 감사 절에 기록 (실행 명령과 결과, 정책 대조 결과, 발견 사항)
8 loop final --result pass --summary "요약", CLI 가 완료 커밋 태그 보관을 처리
9 미충족 발견 시 loop final --result fail --summary "사유" 기록 후 보완 항목을 plan revise 로 추가하고 2절로

## 5 중량 모드

- 중량은 DOMANGCHA 전체 설치본(라우터, 증거 게이트, 승인 게이트)을 그 항목에만 적용한다는 뜻
- 모드가 중량인 항목은 start 시 heavy_doc (기본 .claude/heavy/CEO.md) 를 읽고 그 규정을 해당 항목에만 적용
- 중량 규정 적용 결과도 pass --notes 에 기록
- 경량 항목에서는 heavy_doc 를 읽지 않음
- /ceo 는 요청 전체를 하네스로 올림, 하네스가 없으면 루프가 먼저 설치를 제안함

## 6 정책 자가학습

같은 실수를 반복하지 않기 위해 감사 실패를 정책으로 승격하고 이후 모든 항목에서 자동 대조함

승격 절차

1 loop fail 로 같은 항목이 policy_promote_after (기본 2) 회 이상 실패하면 CLI 가 승격 후보라고 알림
2 실패 원인이 이 항목 한정인지 다른 항목에서도 재발할 일반 규칙인지 판단
3 일반 규칙이면 loop policy add --title "짧은 제목" --rule "무엇을 하지 말고 무엇을 할 것" --origin audit:Ixx
4 항목 한정이면 정책으로 올리지 않고 수정만 함
5 사용자 개입으로 지적받은 규칙도 같은 방식으로 승격하고 --origin iv_xxxx 를 붙임

규칙 작성 기준

- 관측 가능한 행동으로 씀, "주의한다" "신경 쓴다" 같은 표현 금지
- 어겼는지 여부를 diff 나 명령 출력으로 판정할 수 있어야 함
- 한 정책은 한 가지만 다룸, 두 가지면 두 개로 나눔
- 예: 나쁨 "i18n 을 잘 지킨다", 좋음 "사용자 노출 문자열을 추가하면 같은 커밋에서 ko en 메시지 파일을 함께 수정한다"

재작성과 폐기

- 같은 정책을 policy_rewrite_after (기본 3) 회 이상 어기면 문구가 실행 가능하지 않다는 뜻이므로 폐기 후 더 구체적으로 다시 씀
- 프로젝트 구조가 바뀌어 규칙이 무의미해지면 loop policy retire P00x --reason "사유"
- 정책은 늘리는 것이 목적이 아니므로 실효 없는 줄은 지움

주입 경로

- 매 프롬프트: UserPromptSubmit 훅이 활성 정책을 지시문과 함께 출력
- 세션 시작과 컨텍스트 정리 후: loop resume 출력에 포함
- 항목 감사: 2절 3-g 에서 loop policy check 로 직접 대조
- 따라서 컨텍스트가 초기화되어도 정책은 소실되지 않음

## 7 산출물과 문체

- 커밋 메시지: 항목 커밋 vX.Y.Z-Ixx: 제목, 완료 커밋 vX.Y.Z: 플랜 제목 (CLI 자동)
- 문서 산출물: 개조식, 마침표 없는 종결, 가운뎃점 미사용, 이모지 미사용, 전각 대시 미사용, 버전 표기 v0.0.0
- 설정값은 env 추가 대신 DB 저장과 UI 관리
- 이 절은 에이전트가 내놓는 산출물의 문체이고 사용자에게 보이는 제품 화면은 8절이 규정함

저장소를 읽어본 적 없는 사람이 보는 면이 사용자 화면이고 운영자용 진단 화면은 동작 상태 감사 세 항목만 적용

개발 지시와 제품 화면을 구분

- 사용자의 요구 문장은 기능과 동작으로 구현하고 화면의 제목 설명 배지 메뉴로 그대로 옮기지 않음
- "한눈에 보여줘" 는 정보 구조 변경이지 부제가 아니고 "완전 자동" 은 실행 조건이지 배지가 아님
- "실시간" 은 갱신 방식이 실제로 있을 때만 쓰는 말이고 "중복 메뉴 통합" 은 통합 자체이지 안내 문구가 아님
- 화면에 "요청하신" "구현했습니다" "개선했습니다" "이 화면에서는" "본 시스템은" "사용자 편의를 위해" 금지
- 구현 이유와 기술 설명은 작업 보고와 문서에만 기록

문구

- 현재 상태 알림, 다음 행동 안내, 입력 제약 설명, 오류 해결 안내, 비용 권한 삭제 같은 중요한 결과 고지 중 하나를 하지 않는 문구는 삭제
- 제목을 반복하는 부제, 기능 홍보 문장, 당연한 사용법 삭제
- "간편하게" "스마트하게" "강력한" "혁신적인" "완벽한" "한눈에" "원활한" "최적의" 를 기본 수식어로 쓰지 않음, 제품명과 근거 있는 표현은 예외
- 입력 형식 과금 조건 권한 영향 삭제 범위 복구 가능 여부는 문구를 줄인다는 이유로 지우지 않음

이름

- 저장소에 이미 쓰는 업무 용어와 일반 관례를 먼저 확인하고 통일, 새 이름을 임의로 만들지 않음
- 메뉴는 찾는 대상이나 업무, 버튼은 실제 실행되는 행동, 상태는 실제 상태로 씀
- 결과가 중요한 작업은 대상을 함께 씀 (주문 취소, 연결 해제, 계정 삭제)
- "시작하기" "진행하기" "관리" 처럼 결과가 불명확한 버튼명은 구체적 행동으로 바꿈, 단순 안내를 닫는 "확인" 은 허용
- 같은 행동에 저장 적용 등록 완료를 혼용하지 않고 동작이 다르면 차이를 정의
- 한 대상은 목록 상세 설정에서 같은 이름으로 부름
- 내부 영문 용어 API 이름 변수명 개발 단계명 불필요한 AI 접두어를 사용자 메뉴에 노출하지 않음, 실제 업무에 필요한 전문 용어는 유지

구성

- DB 테이블 서비스 모듈 개발 순서로 메뉴를 만들지 않고 사용자가 업무를 시작하고 끝내는 자리를 기준으로 구성
- 같은 목적의 메뉴 카드 설정은 통합, 하위 기능은 상세 화면이나 탭에 배치, 서로 다른 이름으로 같은 화면에 연결하지 않음
- 목적이 다른 기능을 무리하게 하나로 합치지 않음
- 실제 데이터나 행동이 없는 요약 카드 탭 섹션을 만들지 않음
- 단순 목록과 입력 화면에 소개 페이지 같은 큰 제목 홍보 문구 장식 배지를 넣지 않음
- 첫 화면은 그 사용자가 자주 하는 업무와 판단에 필요한 정보를 우선 배치하고 기능 수를 과시하지 않음

동작

- 버튼이나 메뉴를 만들었으면 UI 요청 처리 저장 또는 외부 작업 결과 확인 UI 재반영 실패 처리까지 실제로 확인
- 금지: 눌러도 아무 일 없는 버튼, 저장 없이 뜨는 성공 알림, 새로고침하면 사라지는 저장 결과, 고정 샘플 수치를 실제 데이터처럼 표시, 결과 확인 없이 표시하는 완료 연결됨 동기화됨, 기능 대신 반복되는 준비 중 알림, 실제 연결 없는 검색 필터 정렬 다운로드 알림
- 미지원 기능은 기본적으로 노출하지 않고 존재와 제한을 알려야 하면 제한 이유와 대안을 함께 표시

상태

- 데이터 없음 조회 실패 로딩 중 권한 없음을 각각 다른 상태로 처리
- 빈 상태는 무엇이 없는지와 다음 행동, 로딩은 진행 중 표시와 중복 실행 방지, 오류는 완료하지 못한 일과 가능한 조치, 권한 제한은 사유와 요청 경로
- 필요하면 마지막 갱신 시각과 갱신 실패를 표시하고 일부 성공은 성공 항목과 실패 항목을 구분
- 실패를 빈 목록이나 0 으로 위장하지 않음
- 스택 트레이스 SQL 토큰 내부 경로를 사용자 화면에 노출하지 않고 진단 정보는 로그에 기록
- 재시도 가능한 작업과 중복 처리 위험이 있는 작업을 구분하고 오류가 나도 입력값은 가능한 범위에서 보존

확인창과 알림

- 조회 이동 저장마다 확인창을 띄우지 않고 삭제 결제 외부 발송 되돌리기 어려운 변경에만 제공
- 확인창에는 대상 영향 실행 버튼을 명시하고 "정말 진행하시겠습니까" 만 보여주지 않음
- 성공은 실제 결과를 확인한 뒤 한 번만 표시하고 계속 알아야 하는 상태를 금방 사라지는 알림으로만 전달하지 않음

일관성과 기본 사용성

- 기존 디자인 시스템과 공통 컴포넌트를 먼저 사용
- 같은 기능은 버튼 위치 색상 의미 날짜 금액 수량 형식 필수 입력 표시 오류 표시 방식을 통일
- 의미 없는 아이콘 이모지 그라데이션 배지 애니메이션을 추가하지 않음
- 아이콘만 있는 버튼에 접근 가능한 이름을 제공하고 색상만으로 상태를 구분하지 않으며 키보드 이동과 포커스 표시를 유지
- 긴 이름 큰 금액 다국어 모바일에서 내용과 동작이 깨지지 않게 함
- 버튼의 로딩 비활성화 상태와 그 사유를 필요한 곳에 표시
- 뒤로 가기 새로고침 직접 URL 접근에서 정상 동작하고 목록으로 돌아왔을 때 검색 필터 페이지 상태를 가능한 범위에서 유지

AI 기능

- AI 가 관여한다는 이유만으로 배지 대화창 설명문을 붙이지 않고 실제 업무에 도움이 되는 자리에만 배치
- 판단 근거 불확실성 검토 필요 여부가 사용자 결정에 영향을 주면 필요한 수준으로 표시하고 검증되지 않은 결과를 확정 사실처럼 쓰지 않음
- 내부 프롬프트 추론 과정 에이전트 이름 개발용 상태 메시지를 일반 사용자 화면에 노출하지 않고 운영자 진단 화면은 목적에 맞게 따로 구분

화면 감사

라우트 메뉴 공통 컴포넌트 화면 문구 주요 사용자 흐름을 확인하고 아래 10문항에 근거와 함께 답함

1 개발 지시나 구현 보고가 화면에 섞여 있는가
2 역할 없는 설명 수식어 배지가 있는가
3 메뉴 이름과 실제 기능이 일치하는가
4 같은 기능이나 용어가 중복 혼용되는가
5 버튼을 눌렀을 때 실제 결과까지 이어지는가
6 표시된 수치와 상태에 실제 근거가 있는가
7 빈 상태 오류 권한 로딩이 구분되는가
8 비용 삭제 보안 등 중요한 안내가 빠졌는가
9 기본 탐색 입력 모바일 접근성에 문제가 있는가
10 수정 때문에 기존 업무 흐름이 깨졌는가

- 대표 사용자 흐름 하나를 끝까지 고쳐 기준을 확인한 뒤 나머지 화면으로 확장하고 첫 화면만 정리한 채 완료로 선언하지 않음
- 단순 문구 변경에 불필요한 구조 개편을 하지 않고 중복 제거는 기존 데이터 권한 연동을 보존하는 범위에서 수행
- 브랜드와 마케팅 면에서는 의도적 시각 표현이 허용되고 업무 화면에서는 위 절제 기준이 우선함

## 9 기능 완결성과 검증

3-h 의 나머지 절반, 8절이 보이는 것을 다루면 이 절은 실제로 동작하는지를 다룸
코드가 있고 화면이 보이고 빌드가 통과하는 것은 완료가 아님
실제 사용자가 브라우저에서 업무를 끝까지 수행하고 결과가 저장되고 재접속해도 유지되고 실패해도 복구 가능해야 완료임

목적과 흐름

- 요청 문장을 나열해 구현하지 않고 아래 사슬을 먼저 적음
  목적 - 진입 경로 - 수행 작업 - 필요한 하위 기능 - 데이터와 상태 - 권한과 외부 의존성 - 성공 결과 - 실패 복구 경로
- "고객 관리" 는 고객 목록 화면 하나로 끝나지 않고 이 프로젝트에 필요한 등록 상세 수정 삭제 또는 비활성화 검색 중복 처리 연결 업무 조회 권한 처리까지 확인해야 함
- 명시된 요구사항, 기존 시스템에서 확인한 사실, 합리적으로 도출한 보완 사항, 확인이 필요한 가정을 구분하고 추측을 확정된 업무 정책처럼 구현하지 않음
- 명백히 필요한 보완은 요청 범위 안에서 스스로 수행
- 금전 처리 데이터 영구 삭제 권한 확대 외부 발송은 기존 근거를 먼저 확인하고 근거가 없으면 필요한 질문만 함

관리 대상의 CRUD 와 생명주기

- 이번 변경이 건드리는 대상마다 아래의 필요 여부와 현재 구현 상태를 확인
  생성 (입력 검증 중복 확인 저장 결과 확인), 조회 (목록 상세 검색 필터 정렬 페이지), 수정 (기존 값 로딩 변경 검증 저장 연관 화면 반영), 삭제 (가능 조건 영향 범위 연관 데이터 처리 결과 반영), 상태 전환 (승인 취소 종료 보관 비활성화 복구 중 업무에 필요한 것)
- 모든 대상에 CRUD 를 기계적으로 붙이지 않음, 거래 기록 감사 로그 외부 원본은 조회와 취소 기록과 보관으로 처리하고 근거를 남김
- 기능이 필요 없는 경우와 구현을 빠뜨린 경우를 구분하고 CRUD 가 일부만 있으면 어느 쪽인지 밝힘
- 삭제로 참조가 깨지는지, 수정 후 목록과 상세가 다른 값을 보여주는지, 중복 제출로 데이터가 두 번 생기는지까지 확인

상세로 이어지는 경로

- 목록의 주요 항목은 해당 항목 상세로, 연결된 객체 이름은 그 객체 상세로, 건수 합계 통계는 그 수치를 구성하는 목록이나 근거 데이터로, 알림은 관련 대상이나 처리할 작업으로, 이력은 해당 변경과 관련 대상으로 이어짐
- 통계에서 목록으로 이동할 때 기간 상태 조직 같은 집계 조건을 유지하고 표시된 수치와 조회 결과가 일치해야 함
- 단순 설명 단위 장식까지 클릭 가능하게 만들지 않음, 클릭 가능해 보이면 반드시 의미 있는 동작이 있어야 하고 상세가 필요한 항목을 텍스트로만 두지 않음
- 행 클릭과 선택 체크박스와 행 내부 버튼이 충돌하지 않게 하고 링크는 새 탭 열기와 키보드 접근을 지원

상세 화면

- 대상의 식별 정보 주요 속성 현재 상태 관련 데이터 가능한 작업을 제공하고 업무에 필요하면 변경 이력을 포함
- 이름과 상태만 보여주는 빈 상세 화면으로 완료 처리하지 않고 반대로 필요 없는 탭이나 빈 섹션으로 채우지도 않음
- 상세 페이지 사이드 패널 모달 중 작업 복잡도 탐색 빈도 직접 링크 필요성으로 선택하고 공유 북마크 재접속이 필요한 상세는 안정적인 URL 로 접근 가능하게 함
- 삭제된 대상 존재하지 않는 ID 접근 권한 없는 대상 오래된 알림 링크로 진입하는 경우까지 처리

UX 설계

- 컴포넌트 배치로 UX 검토를 대신하지 않음, 아래에 실제 화면과 동작으로 답할 수 있어야 함
  어디에서 시작하는가, 현재 대상과 상태를 바로 이해하는가, 가장 중요한 다음 행동이 분명한가, 다른 화면의 정보를 기억해 와야 하는가, 같은 값을 반복 입력하거나 화면을 왕복하는가, 성공 여부와 결과를 확인할 수 있는가, 실수하거나 중간에 나가도 복구 재개할 수 있는가, 데이터가 많거나 없을 때도 쓸 수 있는가
- 검색 필터 정렬 페이지 탭 상태를 적절히 유지하고 입력 중 이탈 저장하지 않은 변경 중복 제출 오래 걸리는 작업 세션 만료로 인한 입력 손실을 고려
- 설명문을 추가하기 전에 구조 명칭 기본값 배치 피드백으로 해결되는지 먼저 판단
- 자주 쓰는 업무는 빠르게, 드문 고급 기능은 필요한 위치에 두고 일괄 작업과 단축 동작은 실제 필요를 확인한 뒤 적용

디자인 시스템

- 기존 디자인 시스템을 먼저 확인하고 재사용하며 없으면 현재 제품에 필요한 범위에서 기준과 공통 컴포넌트를 만듦
- 색상과 의미 (주요 보조 위험 성공 경고 비활성), 글자 (크기 굵기 행간 제목과 본문 위계), 간격과 배치 (여백 화면 폭 정렬 반응형 기준), 컴포넌트 (버튼 입력 선택 표 탭 모달 패널 알림), 상태 (기본 hover focus 선택 비활성 로딩 오류), 데이터 표현 (날짜 시간대 금액 통화 수량 단위 빈 값) 을 일관되게 정의
- 문서에만 정의하지 않고 토큰 공통 컴포넌트 공통 포맷터로 실제 코드에서 재사용되게 함
- 화면마다 임의의 색상 크기 모달 동작 버튼 순서를 만들지 않고 같은 역할은 같은 방식으로 동작하게 하며 기존 컴포넌트로 되는데 유사 컴포넌트를 새로 만들지 않음
- 디자인 시스템 구축을 이유로 불필요한 프레임워크나 대규모 재작성을 도입하지 않음

화면부터 저장 결과까지 연결

- 아래 연결 중 하나라도 빠지면 미완성
  UI - 이벤트 - API 또는 Route - 권한 검증 - 서비스 - DB 또는 Job 또는 외부 연동 - 처리 결과 - UI 재반영 - 실패 복구
- 백그라운드 작업은 접수와 완료를 구분하고 진행 상태 실패 재시도 결과가 사용자에게 반영되게 함
- 프런트엔드에서 버튼을 숨기는 것으로 권한 검증을 대신하지 않고 서버에서 대상 데이터 접근 권한과 작업 권한을 검증
- 동시 수정 중복 요청 부분 실패 외부 응답 지연이 실제로 가능한 작업에만 업무에 맞는 무결성과 복구 방법을 적용하고 모든 기능에 같은 장치를 붙이지 않음

놓친 요구사항 탐색

- 요청마다 아래를 확인해 실제로 관련된 누락만 보완
  역할별 접근 권한과 조직 사용자 간 데이터 분리, 필수값 중복값 잘못된 입력 최대 길이 경계값, 빈 데이터 대량 데이터 긴 텍스트 모바일, 날짜 시간대 통화 소수점, 검색 결과와 집계 수치의 정합성, 연결 데이터의 수정 삭제 영향, 외부 연동 실패 시간 초과 세션 만료, 중복 실행 동시 수정 재시도, 필요한 이력 로그 복구 경로, 조회 성능 과도한 호출 불필요한 비용, 기존 기능과의 충돌 및 회귀
- 가능한 모든 기능을 추가하라는 뜻이 아님, 목적 달성에 필요한 누락과 근거 없는 기능 확장을 구분하고 목적과 무관한 기능 설정 추상화를 늘리지 않음

브라우저 검증

- 브라우저는 `ego-browser` 스킬이 설치돼 있으면 그것(먼저 `ego-browser skill` 실행), 없으면 Claude-in-Chrome — 둘 중 하나라도 있으면 Playwright는 쓰지 않음
- 코드 검토 API 성공 응답 빌드 통과로 UI 검증을 대신하지 않고 실제 브라우저를 열어 사용자가 보는 화면에서 클릭 입력 이동 저장 재조회
- 변경한 기능에 해당하는 시나리오를 수행
  1 정상 진입 경로로 접근
  2 필요한 데이터를 생성하거나 선택
  3 목록에서 찾고 상세로 진입
  4 값을 수정하고 목록과 상세 반영 확인
  5 새로고침과 재접속 후 저장 결과 확인
  6 직접 URL 접근과 뒤로 가기 확인
  7 삭제 취소 비활성화 등 해당 생명주기 확인
  8 잘못된 입력 빈 결과 실패 권한 제한 확인
  9 관련 기능에 영향 없는지 확인
  10 주요 화면 크기에서 잘림 겹침 스크롤 클릭 영역 확인
- 콘솔과 네트워크 요청을 함께 보되 오류가 없다는 사실만으로 정상 동작을 판단하지 않고 기대한 데이터와 상태 변화가 실제로 일어났는지 확인
- 검증은 테스트 환경 계정 데이터를 우선 사용하고 검증을 이유로 운영 데이터 삭제 실제 결제 외부 발송을 하지 않음
- 브라우저나 외부 연동에 접근할 수 없으면 가능한 다른 검증을 수행하고 직접 확인하지 못한 범위를 명확히 기록, 실행하지 않은 테스트를 통과했다고 보고하지 않음

자가점검과 재검증

- 첫 구현 후 아래 관점으로 다시 감사
  요구사항 누락, CRUD 상세 관련 화면 연결 누락, 문구 명칭 디자인 불일치, 불필요한 단계와 사용성 문제, 잘못된 성공 표시와 상태 불일치, 권한 데이터 무결성 문제, 오류 실패 복구 처리 누락, 기존 기능 회귀, 불필요한 과설계
- 발견한 문제는 목록만 만들지 말고 현재 범위에서 해결하고 수정 후 문제를 발견한 시나리오와 직접 영향받는 흐름을 다시 검증
- 같은 문제가 반복되면 문구나 예외처리를 덧붙이지 말고 데이터 흐름 상태 관리 공통 컴포넌트에서 원인을 찾음
- "완벽하다" "버그가 없다" 고 보장하지 않음

완료 조건

아래 8줄을 모두 충족해야 완료이고 충족하지 못한 줄은 남은 제한으로 따로 적음

1 요청한 기능과 필수 후속 작업이 구현되어 있음
2 필요한 CRUD 와 상세 조회 경로가 연결되어 있음
3 실제 저장 결과와 화면 표시가 일치함
4 공통 디자인 용어 상호작용 기준을 지킴
5 주요 정상 실패 시나리오를 검증함
6 수정으로 영향받은 기존 흐름을 확인함
7 발견한 차단 오류를 해결하고 재검증함
8 확인하지 못한 사항과 남은 제한을 구분해 기록함

- 보고는 변경 내용, 실제 검증한 흐름, 발견하고 수정한 문제, 남은 제한만 간결하게
- 테스트 환경에 접근하지 못했거나 연동이 막혀 있으면 그 부분은 완료로 처리하지 않음
- 문제가 많으면 데이터 손상 권한 오류 핵심 흐름 중단을 먼저 해결하고 CRUD 상세 연결 상태 처리 UX 디자인 일관성 순으로 진행
- 큰 작업은 검증 가능한 단위로 나누되 전체 점검 목록을 유지하고 일부 화면 개선을 전체 완료로 표현하지 않음
- 이미 승인받은 범위의 남은 작업을 "원하시면 진행하겠습니다" 로 넘기지 않고 실제 차단 사유가 없으면 수정과 검증을 계속함
